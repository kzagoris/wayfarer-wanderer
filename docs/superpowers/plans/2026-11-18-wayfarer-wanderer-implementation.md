# Wayfarer Wanderer implementation plan

**Goal** — Open or create a Java or Kotlin/JVM application or Spring Boot service, edit it, run its tests and debug it in a standalone .NET desktop IDE. A shared editor fix should reach Passenger and Wayfarer Wanderer from one maintained source.

**Architecture** — Build the desktop host in C# and Avalonia. Consume Passenger libraries at a pinned source revision. Give each window its own project session and keep JVM tools in child processes. The JVM project host owns build evaluation, and the .NET session owns buffers, semantic edits and running operations.

**Specification** — Read the [product and architecture specification](../../initial-spec.md). This plan covers its three delivery milestones. The first is ready to implement. The second selects integrations by running fixtures. Tasks in the third consume those decisions.

**Execution** — Use `superpowers:executing-plans` for inline implementation. For each numbered task, first add the named failing check, run it and record the observed failure. Implement the smallest change that satisfies it, rerun it with adjacent regressions, and commit the passing slice. Use `superpowers:test-driven-development` for the fixtures, `omabox` for GUI work on the Omarchy workstation, and `superpowers:verification-before-completion` at each milestone. All paths below are proposed Wayfarer Wanderer paths unless marked Passenger. Commands targeting proposed files become available in the task that introduces them.

## Constraints and review focus

- Match the Passenger pin's SDK, package versions and lockfiles. At the spec baseline the SDK is 11.0.100 with latestFeature roll-forward, target net11.0 and Avalonia 12.1.6. Record the exact tools used on each verification machine.
- Address Windows, macOS and Linux. Existing Gradle builds can use Groovy or Kotlin DSL. New Gradle builds use Kotlin DSL under the spec's proposed default. Select supported JVM tool versions from working repositories in milestone 2.
- Give every operation one action, shared by its entry points. Extract shared code when both consumers can exercise it. Preserve per-window isolation and Passenger's trust and child-process lifetime rules.
- Review the failures most likely to hide behind a green smoke test: missing runtime theme resources (task 2), stale import replies after a workspace switch (task 4), incomplete cross-language edits (task 5), an orphaned service after a debug session (task 6), and a generator colliding with an existing destination (task 8).

## Milestone 2 — Prove JVM interoperability before selecting the backends

### 4. Import the same project model that tools actually use

**Decision (2026-11-20)** — Wayfarer Wanderer asks the build tool for the project model in an external JVM process, following Passenger's project host (`Passenger.Host`, driven by `Passenger.Workspace/ProjectHost.cs`). It never infers the model from build-file text. The in-process reader in `src/WayfarerWanderer.Jvm/WorkspaceImport.cs` (Maven XML, a regex over Gradle `include` lines, standard folder names, empty classpaths) was an interim and is removed by this task. Until a folder is trusted, the window shows its files and offline highlighting only, with no modules.

- [ ] Commit self-contained inputs and expected outputs under `tests/fixtures/jvm/`: a multi-module Maven reactor with a Java main and Kotlin library, a Gradle multi-project build with a Kotlin main and Java dependency, Boot services on both tools, and IntelliJ module folders without a build tool. Cover both Gradle dialects, generated sources, a non-standard source folder, a source set added by a plugin, a Maven profile, per-module JDKs and distinct import/runtime JDKs. Pin wrappers, fixture dependencies and expected source locations and classpaths. Use precision-sized fixtures that can be rebuilt by their wrappers independently of Wayfarer Wanderer.
- [ ] In `tests/WayfarerWanderer.Tests/WorkspaceImportTests.cs`, open files before trust, edit a buffer and observe ChildProcesses.Started. Add a marker in each fixture's wrapper/import entry to catch starts outside that hook. Adapt the trust denial to name the current host and verify Passenger keeps its own text. Require zero host, wrapper, daemon or semantic import launches until the enclosing repository is trusted, and no modules shown before trust. Test missing JDK selection/retry, a missing wrapper with an explicitly configured build tool, an absent tooling JVM, and the host crashing or hanging mid-request. Move the existing trust, import and stale-snapshot cases from `JvmRuntimeFoundationTests.cs` here and point them at the host.
- [ ] Implement the external host under `jvm/project-host/` with `src/WayfarerWanderer.Jvm/ProjectHost.cs` as its client, feeding `WorkspaceSnapshot.cs` and `src/WayfarerWanderer.App/ProjectSession.cs`. Start one host per tooling JVM, shared by windows as Passenger's `ProjectHosts` shares one per SDK, on a tooling JVM separate from the project's JDKs (see the decisions in `docs/archive/task-4-handoff.md`). Build it through its own checked-in Gradle wrapper in jvm/project-host, with pinned distribution checksum, dependency locks and verification metadata. Add `tools/build-jvm-host.py` and an incremental MSBuild build/publish target to stage its JAR and runtime dependencies under artifacts/jvm-host; test locating them from a different working directory.
- [ ] Use Passenger's host protocol framing so both hosts behave alike and the client can follow `ProjectHost.cs`: one UTF-8 JSON object per line on stdio, logs on stderr. Each request carries an id and the import generation. The host answers with partial results as modules are evaluated, then a result or an error, and supports `cancel`. Its first line names the protocol version and tooling JVM it runs on, or why it cannot start. Name the model's messages and fields after the Build Server Protocol's build targets, sources, dependency modules and JVM run environments, so a BSP server (such as Microsoft's Gradle build server) could replace an evaluator later.
- [ ] Evaluate Gradle through the wrapper-compatible Tooling API with an injected init script and custom tooling model builder that returns exactly Wayfarer's model; do not rely on the built-in Eclipse or IDEA models. Evaluate Maven with the wrapper-selected Maven runtime loaded in an isolated class loader, resolving active profiles. Read IntelliJ `.iml` modules and their library and JDK tables in the host, without a build tool. Capture stable module and source-set identities, roots including Kotlin and generated sources, ordered compile/runtime/test classpaths, import/compile/runtime JDKs, tasks and main classes. Publish a complete snapshot per generation. Record the tooling JVM used to run the host, each server and adapter independently of the project's JDKs. Choose bundled versus locally discovered tooling JVMs after checking versions, distribution rights and cold-start cost. An absent or incompatible tooling JVM should identify the affected tool and offer recovery.
- [ ] Delete the in-process reader (`WorkspaceImporter`, its Maven, Gradle and IntelliJ adapters and `WorkspaceLayouts`). Make build, test, launch and debug take classpaths and JDKs from the snapshot instead of resolving them separately at launch. Confirm with a search that no caller parses build files outside the host.
- [ ] Change a dependency, compare the new snapshot with both language services' effective roots, dependencies and JDKs, then remove it. Deliberately fail evaluation, repair it and switch workspaces while an old response is pending. Assert the last good snapshot stays visible as stale, affected semantic actions are disabled, old responses are dropped and edits survive. Record cold import (cold and warm Gradle daemon), warm reopen and host memory. Keep protocol examples and a structured comparison for both tools in `docs/validation/jvm-backends.md`.

## Milestone 4 — Add the IntelliJ backend after the first release

The first release ships only the open backend. This milestone starts after milestone 3 is released and does not gate it.

### 10. Offer the IntelliJ server as a subscription backend

- [ ] Add a language-backend setting with `open` (default: JDT LS, the Kotlin server and the Maven Kotlin class bridge) and `intellij` (JetBrains' IntelliJ LSP server for both languages). - [ ] Check the licence with the server's `license` command before switching. On a missing, invalid or expired licence, show the reason, stay on `open` and keep a visible notice. - [ ] Parameterize the language fixtures by backend: completion in both directions on Maven and Gradle, definition, references, formatting, mixed rename with undo, and server-kill recovery. - [ ] Document the setting, the licence requirement and the fallback in the README and onboarding. Confirm that redistribution terms still exclude bundling the server, so users install it themselves, as they install the Kotlin server today.
