# Wanderer release specification and implementation plan

**Goal.** A maintainer can rehearse a release from a branch, inspect the exact downloads and test evidence, then dispatch a tagged build that publishes a complete GitHub Release for Wayfarer Wanderer.

## How Passenger ships

Reference checkout: Passenger commit `2044e49b5`. Its [.github/workflows/release.yml](../../../../passenger/.github/workflows/release.yml) is the orchestration reference. The platform scripts under Passenger's `tools/package-{win,mac,linux}.sh` own packaging, `release-common.sh` owns shared publishing logic, and `release-notes.sh` selects the release text.

1. A maintainer manually dispatches **Release**. A tag push alone does nothing. Dry run defaults on. Publication requires a numeric `vX.Y.Z` tag. Branch rehearsals use an exact release tag on HEAD if present, otherwise the project version.
2. Passenger calls its reusable gating test workflow, with an explicit skip option. It builds the mobile debug relays, six desktop packages (Windows, macOS and Linux, each x64 and arm64), and four separate Linux container-tool archives. Some lanes cross-build. macOS and Windows can sign with configured credentials.
3. Each desktop job checks the assembly's product version against the version plus the full commit SHA. The collector requires an exact filename set, validates the Windows channel feeds, hashes the downloads into `SHA256SUMS`, and prepares version-specific notes or commit-derived notes.
4. A rehearsal retains the bundle for seven days. Only the final job has repository write permission. It publishes the collected files with `gh release create --verify-tag`. Runs serialize per ref.

## Wanderer release contract

Reuse [the packager](../../../tools/package-release.py), [payload inventory](../../../tools/check-publish.py), [acceptance runner](../../../tools/acceptance.py) and [installed-platform validation record](../../validation/release.md). Wanderer already performs locked RID restore and self-contained publish, and creates Velopack, DMG and Linux tar packages. Its recorded Windows x64 evidence covers a portable install. Setup installation and current-commit qualification are still needed.

**Proposed rollout.** Rehearse Windows x64 first. The release targets are win-x64, linux-x64 and osx-arm64. Each public release declares its matrix in version control before dispatch. Every declared target must pass installed acceptance on a compatible runner. A cross-build alone qualifies for a rehearsal artifact only. Keep musl desktop targets experimental until the native libraries and installed application pass on musl. Passenger's musl downloads are container tools. Wanderer's corresponding build dependency is its Java/Kotlin project host.

| Target | Proposed public files |
| --- | --- |
| Windows | `WayfarerWanderer-windows-<arch>.exe`, `releases.win-<arch>.json`, and the exact versioned full package named in that feed |
| macOS | `WayfarerWanderer-macos-<arch>.dmg` |
| Linux | `WayfarerWanderer-linux-<arch>.tar.gz` |
| All | `SHA256SUMS` covering every public download above, plus release notes as the GitHub Release body |

Suppress portable Windows packages during rehearsal and publication. Shipping a Velopack feed establishes the distribution format. In-app update UI and behavior require separate acceptance criteria.

## Implementation sequence

- [ ] **1. Establish version identity.** Add manual `.github/workflows/release.yml` with default `dry_run=true`, read-only permissions, pinned actions and per-ref concurrency. Resolve the version once. For publication require an existing canonical numeric tag matching Wanderer's `Directory.Build.props` (currently 0.1.0). Pass version and SHA explicitly into `tools/package-release.py`, MSBuild publish, Velopack and macOS bundle metadata. Check the packaged app assembly reports `X.Y.Z+<full SHA>`. Exercise branch rehearsal, branch publication rejection, malformed tag and mismatched props before enabling upload.
- [ ] **2. Make one package reproducible from a clean checkout.** Start with win-x64. Install the SDK from `global.json`, JDK 21 and the runtime needed by the repository's pinned vpk tool. Invoke the manifest tool even when a global vpk exists. Build and test the pinned Gradle host with `python tools/build-jvm-host.py --test`. Keep locked RID restore and inventory checks. Give every RID fresh staging and output directories. Pass an explicit Velopack channel per RID. The present Windows packer writes to the requested file's parent and records the requested filename without checking it exists. Inventory actual outputs, normalize the installer name, and record relative filenames. Verify two consecutive builds with different versions leave only the second version in the collected files.
- [ ] **3. Gate the installed product.** Run the solution tests and named acceptance selectors. Install Setup in a clean Windows user profile, locate the installed executable and run `python tools/acceptance.py --app <installed-executable> --results <fresh-directory>`. Repeat from the copied app on macOS after unmounting the DMG, and from the installed prefix on Linux after removing the extracted archive tree. Exercise the installed app from a working directory outside the checkout with an isolated profile. Check the staged JVM host, starter templates, notices, native libraries and forbidden Passenger payloads. Prove an installed starter imports and runs using the documented JDK. Preserve TRX, logs, inventory and results per RID even on failure. The runner also invokes source tests and launches its packaged process with the repository as its working directory today. Adjust that path and distinguish installed smoke evidence from source-suite counts. Demonstrate failure by removing the installed project host.
- [ ] **4. Expand the matrix and signing.** Add each qualified RID to the checked-in release matrix with its build runner and installed-test runner. For macOS set the bundle version, sign nested binaries and the app, then sign the DMG and notarize/staple when configured. On Windows apply the configured signing identity through vpk. Verify actual signatures and record unsigned, ad hoc, signed or notarized status per asset. Fail on invalid or partial signing credentials and remove temporary keys. Exercise the credential-free rehearsal, then the signed path when credentials are available. Record each successful installed run in the validation document.
- [ ] **5. Assemble and rehearse.** Add a collector under `tools/` that reads per-RID outputs in separate directories, rejects missing, duplicate or unexpected public files, and checks each feed's version, channel-specific package name and SHA-256 against the actual package. Generate and independently verify `SHA256SUMS` after signing. Read `docs/release-notes/X.Y.Z.md` for publication. Allow a commit summary for branch rehearsal. Upload the assembled bundle for seven days and keep test evidence separately. Test rejection of a missing installer, corrupt package and stale feed. Require passing tests for publication. Passenger's optional test bypass is unnecessary for the first rollout.
- [ ] **6. Publish the tested bundle.** Give only the final tagged publish job `contents: write`. Download the exact artifact assembled by this run, verify checksums again, then create the release with its verified tag, notes and public files. An existing published release must fail closed. On interrupted upload, inspect the draft's tag, commit and asset hashes before resuming it. Document recovery in `docs/validation/release.md`. Never promote a branch rehearsal artifact into a tagged release.

## Maintainer rehearsal and first release

Once the workflow exists on the default branch, dispatch `gh workflow run Release --ref <branch> -f dry_run=true`. Inspect the assembled files, checksums, installed-run reports and signing status. For publication, commit the version, supported matrix and notes together, tag that commit, push the tag, then dispatch `gh workflow run Release --ref vX.Y.Z -f dry_run=false`. The first release is accepted when the public asset list matches the declared matrix, downloaded checksums verify, and every listed platform has an installed-run report for the tag's SHA.
