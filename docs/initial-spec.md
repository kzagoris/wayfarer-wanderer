# Wayfarer Wanderer
## Initial product and architecture specification · draft for review

Wayfarer Wanderer is a standalone .NET desktop IDE for Java and Kotlin/JVM developers working on Maven applications, Gradle applications and Spring Boot services. IntelliJ IDEA is the reference for the daily workflow. Passenger is the reference for the implementation. Both products should benefit from the same fix to a shared editor, terminal or debugger protocol component.

**Agreed direction.** Share components with Passenger and follow its architecture so future features can move between the products. The initial release supports both opening existing repositories and creating new Java or Kotlin/JVM applications and Spring Boot services with either Maven or Gradle. Proposed below are the integration mechanics, feature depth and acceptance criteria. IntelliJ plugin compatibility, Android and Kotlin Multiplatform are separate scope decisions.

The repository uses the slug `wayfarer-wanderer`. Use `WayfarerWanderer` for the .NET solution, projects and namespaces.

## A first session

From the welcome screen or File menu, a developer selects **New Project**, chooses a command-line application or Spring Boot service, then selects Java or Kotlin/JVM and Maven or Gradle. They enter the project name and destination, review the group, artifact, base package and JDK, and select **Create**. Wayfarer Wanderer opens the generated project through its usual workspace import. The developer can run the starter test and launch the application directly from the IDE.

For an existing project, a developer opens the root of a mixed Java/Kotlin Spring Boot repository. They can read and edit files immediately. Once they trust the repository, Wayfarer Wanderer imports the build and shows modules, packages, production and test sources. If a JDK is missing, the import view identifies which tool needs it and offers a JDK selector and retry. The editor keeps unsaved changes throughout import and recovery.

The developer follows a call from a Java controller to a Kotlin service, finds its usages, changes the implementation and runs its JUnit test. A failure opens at the relevant source line. They launch the service with a named profile, send a request and stop at a breakpoint in the service. The Debug window shows the stack and local values. Stop ends the launched service and releases its port. The same edit, test and debug loop works for ordinary command-line applications.

## Architecture and ownership

Use C#, .NET and Avalonia for the desktop application. Follow Passenger's window, workspace session, service and external-tool boundaries. A window owns editor views and tool windows. Its project session owns the imported workspace, language clients and running operations. Closing or switching a workspace cancels its work, drops stale diagnostics and releases its processes. JVM tooling runs outside the UI process.

The following mapping is based on the Passenger checkout at revision `2044e49b5`. Reuse classifications are source-inspection findings and proposals. Binary compatibility and packaging still need a build demonstration.

| Passenger component | Wayfarer Wanderer design | Boundary to preserve |
|---|---|---|
| Passenger.Text and Passenger.Editor | Reuse the text model, undo, CodeEditor, keymaps, decorations and gutter hooks. | The editor generates resource keys from Passenger.App theme files. Share those build inputs and supply the corresponding tokens, icons and styles at runtime. Java and Kotlin publish decorations through the host. |
| Passenger.Terminal | Reuse the terminal emulator, view and session. | This library directly depends on Editor, Avalonia and Porta.Pty. Include its theme and native runtime dependencies in the packaging check. |
| Passenger.Vcs and Passenger.App/Vcs | Reuse the Git, diff and merge logic. Extract the needed views from App. | The merge window uses internal diff positions exposed to the Passenger assembly. Give both hosts a tested API for these positions when extracting that view. |
| Passenger.Core | Share process lifetime management, workspace trust and common utilities. | Audit .NET-specific dependencies and supply the host's product name in shared user-facing messages. |
| Passenger.App | Follow ProjectSession and ActionRegistry. Extract docking, actions and tool-window presentation as each second consumer needs them. | The action context and debug state belong to App today. Wayfarer Wanderer composes its own session. Keep concrete C# services out of shared action, run and test presentation. |
| Passenger.Lsp and Passenger.Languages | Extract the generic language client and TextMate host. | Their current projects bring Roslyn, web-server build targets or workspace-specific code. Package syntax grammars for Java, Kotlin, Gradle scripts, properties and YAML so basic highlighting works before trust and import. |
| Passenger.Dap and Passenger.App/Debugging | Share DapConnection and extract reusable debug views from App. | Passenger.Debugger implements the CoreCLR engine. Wayfarer Wanderer supplies a JVM adapter, launch, attach and source mapping. |
| Passenger.Workspace and Passenger.Host | Follow the external project-host pattern. | Define a JVM workspace protocol with modules, source sets, classpaths, toolchains, entry points and tasks. Passenger's MSBuild evaluation and protocol stay in Passenger. |

A clean build resolves the complete pinned source tree, including its generators and theme inputs. Align the host target framework, SDK selection, centrally managed package versions and locked restore with that revision. The current baseline selects SDK 11.0.100 with feature-band roll-forward. [Editor theme inputs](https://github.com/Zaneris/passenger/blob/2044e49b52742eea87acbf6a5901a108d2778719/src/Passenger.Editor/Passenger.Editor.csproj) · [Git library boundary](https://github.com/Zaneris/passenger/blob/2044e49b52742eea87acbf6a5901a108d2778719/src/Passenger.Vcs/Passenger.Vcs.csproj) · [SDK policy](https://github.com/Zaneris/passenger/blob/2044e49b52742eea87acbf6a5901a108d2778719/global.json)

**How features travel.** Keep Wayfarer Wanderer in [its own repository](https://github.com/kzagoris/wayfarer-wanderer). Proposed starting point is a pinned Passenger source revision with project references for reusable libraries. A reproducible checkout resolves that revision without relying on adjacent developer folders. Keep shared changes in one maintained source tree. A revision update runs Passenger's affected tests and Wayfarer Wanderer's JVM acceptance cases. A full fork would ease the first build but require repeated merges of product-specific changes. Versioned packages can replace source references when stable artifacts exist.

For example, an upstream accessibility fix in CodeEditor should reach Wayfarer Wanderer through a revision update. A future CPU profiler would reuse applicable views, actions and session lifecycle, while a JVM collector would supply its data. Each feature registers one action per operation so menus, shortcuts, Find Action and future agent commands invoke the same behavior. Introduce a shared interface when a second implementation demonstrates the need. This design requires no third-party plugin framework for the initial release.

### What a future feature needs to contribute

A feature that acts on a project gets its module and selection from the active window's session, declares its command and availability once, and publishes results to the relevant view. Its backend owns tool-specific behavior. For example, a JVM test runner supplies identifiers, outcomes and source locations. The test tree owns selection and rendering. A future change to the tree can benefit both products, while a new JVM test framework only needs to supply compatible results. Verify extracted presentation code with existing Passenger tests and a Wayfarer Wanderer fixture against the same source revision.

Passenger source anchors for the first extraction review include [ProjectSession](https://github.com/Zaneris/passenger/blob/2044e49b52742eea87acbf6a5901a108d2778719/src/Passenger.App/ProjectSession.cs), [ActionRegistry](https://github.com/Zaneris/passenger/blob/2044e49b52742eea87acbf6a5901a108d2778719/src/Passenger.App/ActionRegistry.cs), [the LSP build dependencies](https://github.com/Zaneris/passenger/blob/2044e49b52742eea87acbf6a5901a108d2778719/src/Passenger.Lsp/Passenger.Lsp.csproj) and [DapConnection](https://github.com/Zaneris/passenger/blob/2044e49b52742eea87acbf6a5901a108d2778719/src/Passenger.Dap/DapConnection.cs).

## JVM services and user-visible behavior

### New Project

Register one action for the welcome screen and File menu. The JVM layer owns the generator. The proposed first release ships versioned templates and compatible wrapper files with distribution notices. Generation works offline with a local JDK. The first build may need network access for the wrapper distribution and dependencies. Show the failed download and offer retry against the generated files.

For every combination, generate the build descriptor, wrapper, source and test roots, runnable entry point, passing JUnit test, build-output ignores and a named application launch configuration. Use Kotlin DSL for new Gradle projects. Accept both Groovy and Kotlin DSL on import. A Boot starter includes a sample HTTP handler and a test for it. Pin compatible Boot and Kotlin plugin versions in the templates, including Spring compiler support for Kotlin Boot services. Leave Git initialization to the developer.

Validate the selected JDK, coordinates, package identifiers and destination before generation. Offer a local JDK picker if discovery fails. Stage files alongside the destination and publish only a complete project into a new or empty folder. On collision, cancellation or write failure, preserve existing entries and clean up files owned by the generation attempt. Once published, keep the project available for import retry. Apply Passenger's trust rules before invoking the wrapper or starting language imports. Creating a project inside an existing untrusted repository requires a separate decision to trust the enclosing repository. [WorkspaceTrust](https://github.com/Zaneris/passenger/blob/2044e49b52742eea87acbf6a5901a108d2778719/src/Passenger.Core/WorkspaceTrust.cs)

### Workspace model and mixed-language edits

The JVM project host owns the last successfully evaluated workspace model. For Gradle, prototype the Tooling API against the selected wrapper distribution. For Maven, prototype project evaluation and dependency resolution against the wrapper-selected Maven version. Record the JVM used for import separately from each module's compile and runtime toolchains. Publish a versioned snapshot of module identities, source sets, generated roots, ordered classpaths and toolchains. Build, test and launch select targets from that snapshot and execute using the project's build configuration. Hold every importer behind workspace trust.

The .NET project session coordinates language services. Where a server performs its own import, compare its effective roots, dependencies and JDK against the host snapshot. A disagreement marks the module's semantic model stale and suspends affected refactorings until reimport succeeds. Discard results from older imports. Verify agreement on Maven and Gradle fixtures after adding and removing a dependency.

For navigation, ask the calling document's backend to resolve the symbol and map the result to the declaration in the workspace, including a declaration in the other language. For rename, the session owns a single preview and edit transaction. Require a backend or coordinated implementation that can establish symbol identity and account for usages in both languages across affected modules. Matching two incomplete lists cannot establish coverage. Revalidate workspace and document versions before applying edits. If coverage is uncertain, a file changed, or edits conflict, explain the reason and leave all documents intact. A successful rename updates declarations, imports and usages together and supports undo as one operation. Prove this on known-reference fixtures before selecting the backend.

### Developer workflows

- **Import and build.** Recognize Maven roots and reactors, Gradle settings in Groovy or Kotlin DSL, subprojects and source sets. Prefer the repository wrapper. Offer a configured installation when the wrapper is absent. Obtain evaluated dependencies and toolchains from the build tooling. Reimport after build-file changes, retain the last successful model on failure and mark it stale. Show the failed task, output and retry action. Workspace trust applies before wrapper execution or automatic language-server import.
- **Editing.** For both languages provide completion, diagnostics, definition, references, formatting and rename with a reviewable multi-file edit. Route each document to its owning language service. Validate navigation and references across Java/Kotlin boundaries in both directions. An incomplete cross-language rename must be reported before applying a partial change.
- **Language backends.** Evaluate Eclipse JDT LS for Java and the standalone JetBrains Kotlin language server for Kotlin. The Kotlin project describes its backend as alpha and partly closed source. Check the distribution terms of the actual binaries and compatibility with Passenger's open-source dependency policy before selecting a bundled backend. Verify standalone import, mixed-source accuracy, concurrent server resource use and recovery on a real build. [Eclipse JDT LS](https://github.com/eclipse-jdtls/eclipse.jdt.ls) · [Kotlin language server](https://github.com/Kotlin/kotlin-lsp)
- **Language backend setting.** The first release ships only the open backend described below. A later release adds the IntelliJ backend and a setting that chooses between them. The *open* backend is the default and needs no subscription: JDT LS for Java and the standalone JetBrains Kotlin server for Kotlin. On Maven, Wayfarer compiles Kotlin with the wrapper and attaches the classes to JDT LS so Java sees Kotlin declarations. The *IntelliJ* backend is for developers with a JetBrains subscription. It uses JetBrains' IntelliJ language server ("Java and Kotlin by IntelliJ IDEA"), which serves both languages from one project model, and starts no JDT LS. The setting is per user, with an optional per-workspace override. The user's own licence activates the IntelliJ backend, through a licence file or a JetBrains licence server URL. Wayfarer never ships a licence and keeps no credential beyond the path or URL the user enters. Check the licence before switching, with the server's `license` command. If it is missing, invalid or expired, name the reason, keep the open backend and leave a visible notice. Switching restarts the language services without losing unsaved buffers or undo history. Both backends must pass the same editing, navigation, rename and recovery fixtures, and each is measured separately. Refactorings stay gated per backend on proven cross-language coverage. [IntelliJ IDEA goes LSP](https://blog.jetbrains.com/idea/2026/08/intellij-idea-goes-lsp/)
- **Run and debug.** Persist the module, main entry point, working directory, arguments, environment and project JDK for each named launch configuration. Distinguish the JVM that runs a language service from the toolchain required by the project. Support Kotlin top-level main functions, breakpoints, step, continue, stack frames, locals and stop. Evaluate Microsoft's Java debug server with Passenger's DAP client and verify Kotlin line mapping separately. [Java debug server](https://github.com/microsoft/java-debug)
- **Tests.** Delegate JUnit execution to the selected module's Maven or Gradle build. Support a class, a method and a module suite. Show passed, failed, skipped and cancelled results, failure text and source navigation. Associate results with the current invocation so an old report cannot turn a failed build green.
- **Spring Boot.** Recognize a Boot application within a Maven or Gradle module. Allow selection among multiple applications. Support run, debug, profile selection, application arguments, live console output, stop and restart. Endpoint discovery, bean inspection and framework-specific refactorings are candidates for later releases.

**Launch ownership.** Prototype a direct JVM launch of the selected main class after the build tool compiles it, including Boot's application classpath, profile, arguments and environment. Verify parity with the project's configured run task on the fixtures. If a build-task launch is needed, track the specific launched application and its children so Stop releases the service port and preserves unrelated processes and shared daemons. Verify how the Java debug adapter starts, which language service it requires, and how it resolves Kotlin-only source locations before committing to it.

## Acceptance and sequencing

| Fixture | Observable acceptance |
|---|---|
| New project in an empty folder | Exercise all eight combinations of application or Boot service, Java or Kotlin, and Maven or Gradle. For each, create the project, import it, build with its wrapper, pass the starter test, and launch from the IDE without editing a build file. Verify console output for an application and a successful HTTP response for a service. |
| Multi-module Maven application, Java entry point and Kotlin library | Open the reactor, navigate between modules, rename a shared declaration safely, build with the wrapper and rerun a failing JUnit method after a fix. |
| Multi-project Gradle application, Kotlin entry point and Java dependency | Import source sets and dependencies, complete a Java member from Kotlin, navigate in both directions, run the application and step into Java. Exercise both Gradle build-script dialects across fixtures. |
| Spring Boot service on each build tool | Launch with a selected profile, hit a handler breakpoint on a request, inspect a local, stop, and restart on the same port. Include a Kotlin handler and a Java handler across the fixtures. |
| Recovery and shared maintenance | Open an untrusted checkout without executing its build. Recover from a missing JDK, failed dependency resolution and terminated language server with edits intact. Upgrade a shared editor component and run editing and breakpoint-gutter checks in both products. |

### Failure and regression cases

| Area | Passing observation |
|---|---|
| Creation | Invalid identifiers, a missing JDK, a nonempty destination and cancellation present recoverable outcomes. Existing files survive and staging files are removed. Exercise a path with spaces and Unicode and a supported long Windows path. Generate offline, reconnect, retry the first build and run the same project. |
| Trust and reimport | Create inside an untrusted Git repository. Verify no wrapper, daemon or server import starts before trust. After a successful import, break a build file, observe the stale state, repair it and verify reimport picks up the change. |
| Language services | Exercise completion, diagnostics, formatting and rename in each language. On each build system, rename a Java member called from Kotlin and a Kotlin member called from Java. Check the preview against known usage sites, preserve an unrelated same-named member, compile and run tests, then undo. Interrupt indexing or edit a target during preview and verify zero partial edits. |
| Tests and recovery | Run a module, class and method, including a Kotlin backtick-named test. Check skipped and cancelled cases and ensure a subsequent build failure cannot display earlier passing results. Terminate a language server with an unsaved edit. Preserve the buffer and undo history, bound automatic retries, and offer manual restart after repeated failure. |
| Launch and debug | Reopen a saved launch configuration and run a Kotlin top-level main. In a Kotlin-only module, bind a breakpoint in source, step and inspect a local. For Boot, select an available port, wait for readiness, send a request, stop and restart on that port while an unrelated JVM stays alive. |

### Delivery milestones

1. **Shared editor.** From a clean checkout, restore pinned sources and render a document in light and dark themes. Verify editor resources, keyboard editing, the breakpoint gutter and a registered action. Inspect the published payload for accidental C# server dependencies. Advance the pin to a compatible upstream editor change and pass the affected Passenger tests and Wayfarer Wanderer checks without copying the fix.
2. **JVM interoperability.** Demonstrate the two build models, bidirectional rename, Kotlin-only breakpoint and Boot stop/restart cases above. Record backend versions, standalone startup requirements, redistribution terms and resource measurements. If a backend fails a required workflow, evaluate another integration or return the scope decision for review. A refused rename demonstrates safe failure only. Successful mixed-language rename remains a release criterion.
3. **First release.** Pass the eight New Project combinations, existing-project workflows and recovery cases on the proposed Windows, macOS and Linux targets. Record cold import, warm reopen, completion latency and peak memory on named hardware and fixtures. Use the phase-two baseline to agree budgets and verify them before release. This release ships only the open language backend.
4. **IntelliJ backend.** After the first release, add the subscription-based IntelliJ backend and the setting that selects it. It must pass the same editing, navigation, rename and recovery fixtures as the open backend.

**Decisions to settle during validation.** Select supported JDK, Maven, Gradle, Kotlin and Spring Boot versions from representative repositories. Record exact backend versions and packaging terms. Measure cold import, warm reopen, completion latency and memory on the mixed-language fixtures before setting performance budgets. The first draft treats keyboard-driven editing, navigation, run configurations and debugging as the IDEA reference points. Broader framework tooling and Passenger features such as MCP automation and profiling can be prioritized independently.
